# AI 审核接入本地模型方案

## 背景

老板希望把"补偿协议-签字一致性比对"业务从云端 qwen-long 切到本地模型，目的：
- 协议正文涉及个人身份信息（姓名 / 身份证 / 金额），不希望上云
- 降低 API 调用成本

服务器：单机 RTX 4090 24GB，已通过 docker 跑 ollama，预拉模型 `qwen3.6:35b-a3b-q4_K_M`（30B 总参 / 3B 激活的 MoE，q4 量化 23GB）。

---

## 当前流程（搞清楚 qwen-long 实际做了什么）

很多人以为"qwen-long 在读 PDF"，**实际上不是**。看 `ReviewAgent.extractOrOcrPdf` + `callAi` 的真实链路：

```
两份 PDF 进来
  │
  ├─ 打印件（有文本层）
  │    └─→ PDFBox 直接抽文本                    ← 纯 Java 库，毫秒级，不调 AI
  │
  └─ 扫描件（无文本层）
       ├─→ PDFBox 渲染每页为 PNG
       └─→ 每页 PNG 调 qwen-vl-plus OCR         ← 云端视觉模型把图还原成文字
                                       │
                                       ▼
                          得到两份"纯文本"字符串
                                       │
                                       ▼
                  qwen-long-latest（一次调用）   ← 对比两份文本，输出 JSON
                                       │
                                       ▼
                          返回审核结果
```

**关键事实**：
- "读 PDF" 是 PDFBox（开源 Java 库）做的，跟 AI 无关
- qwen-vl 只在扫描件出现，作用是 **把图片像素还原成文字**
- qwen-long 拿到的永远是 **纯文本**，它只是个"能吃长上下文的聊天模型"，并未使用它的原生文档解析能力（`fileid://` 那条 `chatWithDocuments` 路径在审核流程里没走）

代码定位：
- `ReviewAgent.callAi`（149-194 行）：路由判断 → 调 `chatLong`
- `ReviewAgent.extractOrOcrPdf`（202-235 行）：PDFBox 抽文本 + 逐页 OCR
- `AiChatService.chatLong`（382-393 行）：实际就是 `chatClient.prompt().options(DOC_OPTIONS).call()`，DOC_OPTIONS 把模型名固定为 `qwen-long-latest`

## 换本地模型后（只动一步）

```
两份 PDF 进来
  │
  ├─ 打印件 ──→ PDFBox 抽文本                       ← 不变
  │
  └─ 扫描件 ──→ PDFBox 渲染 PNG ──→ qwen-vl-plus     ← 不变（仍走云端）
                                       │
                                       ▼
                          得到两份"纯文本"字符串
                                       │
                                       ▼
              ollama @ 4090: qwen3.6:35b-a3b-q4_K_M  ← 这一步从 qwen-long 换成本地
                                       │
                                       ▼
                          返回审核结果
```

| 步骤 | 现状 | 切换后 | 是否变化 |
|---|---|---|---|
| 读打印件 PDF | PDFBox | PDFBox | 不变 |
| 读扫描件 PDF | qwen-vl-plus 云端 OCR | qwen-vl-plus 云端 OCR | 不变 |
| 最后文本对比 | qwen-long-latest 云端 | qwen3.6:35b-a3b-q4_K_M 本地 | **唯一变化** |

## 为什么 OCR 不一起本地化（第一阶段）

服务器有 `qwen3-vl:8b` 镜像，理论上可以替 qwen-vl-plus，但：

1. **24GB 显存被 35B 模型贴满**：实测 35B + flash-attn + 8K 上下文已用 23GB / 24GB
2. **同时加载 qwen-vl 8B 还要 6~8 GB** → 必爆
3. **轮换加载方案不可取**：每页扫描件都"卸 35B → 加 vl → 推理 → 卸 vl → 重加 35B"，单页多花 1~2 分钟，18 页直接超时

**第一阶段只切文本对比**，OCR 继续走 qwen-vl-plus 云端。等加显卡或拆机器了再考虑全离线。

## 实测性能（已在 4090 上跑通）

环境：ollama docker，`OLLAMA_FLASH_ATTENTION=1`，`num_ctx=16384`，`think:false`，`format:json`

| 测试项 | 数值 | 说明 |
|---|---|---|
| 模型加载耗时 | 36 秒 | 首次启动，常驻显存后不再触发 |
| 显存占用 | 23 GB / 24 GB | flash-attn 后腾出 1.5GB headroom |
| GPU 层数 | 39 / 41 layers | output layer 留在 CPU（小开销） |
| Prompt 处理速度 | ~2300 tokens/s | 输入 8K token < 4 秒 |
| 生成速度 | 50 tokens/s | output layer 在 CPU 仍能跑这速度 |
| 5 条规则双文档对比 | **13 秒** | 含 prompt 处理 + 268 token JSON 输出 |
| 指令遵循 | items_count=5 ✅ | 严格按规则数量、顺序、字段名输出 |
| 判断准确性 | amount=mismatched ✅ | 故意改的金额成功识别，其他 4 项 matched |
| Thinking 模式 | 已关闭 | `think:false` + `/no_think` 双保险，无内心戏污染 |

**18 页真实文档预估**：8~12K token 输入 + 1~2K token JSON 输出 → **30~40 秒**，完全在异步轮询（5 分钟超时）容忍度内。

## 数据 / 成本对比

| 维度 | 全云端 | 混合（本地 chat + 云 OCR） | 全离线（本地 chat + PaddleOCR） |
|---|---|---|---|
| 18 页打印件双份 | qwen-long × 1 | **本地 × 1** | **本地 × 1** |
| 18 页扫描件 | qwen-vl × 18 + qwen-long × 1 | qwen-vl × 18 + **本地 × 1** | **PaddleOCR × 18 + 本地 × 1** |
| 数据隐私 | 协议正文全上云 | 打印件正文不出内网，扫描件像素仍上云 | **完全离线** |
| 单次成本 | qwen-long 长 prompt 数毛~数元 | 接近 0（电费） | 接近 0 |
| 单次耗时 | 30~60 秒 | 30~60 秒 | 30~80 秒（PaddleOCR 略慢于 qwen-vl） |
| 印章/手写识别 | 优秀 | 优秀 | 良好（PaddleOCR 略弱，多数场景可接受） |
| 部署成本 | 0 | 0 | docker run 一条命令 |

打印件占协议总量约 90%，混合方案已经能让绝大部分敏感数据不出内网；如果对扫描件像素也要离线，再升级到全离线方案。

## 三档配置切换（已落地）

通过 `application-{profile}.yml` 切换：

```yaml
review:
  ai:
    local:
      enabled: true                 # false=纯云端, true=本地 chat
      base-url: http://192.168.169.205:11434
      model: qwen3.6:35b-a3b-q4_K_M
      num-ctx: 16384
      temperature: 0.2
  ocr:
    provider: qwen-vl               # qwen-vl=云端OCR, paddleocr=本地OCR
    paddleocr:
      url: http://192.168.169.205:8868/predict/ocr_system
```

| 想要的方案 | `local.enabled` | `ocr.provider` | prompt 模板 model_name |
|---|---|---|---|
| 全云端（默认） | false | qwen-vl | 留空 / qwen-long |
| 混合（推荐） | true | qwen-vl | `ollama:qwen3.6:35b-a3b-q4_K_M` |
| 全离线 | true | paddleocr | `ollama:qwen3.6:35b-a3b-q4_K_M` |

`prompt template.model_name` 字段是逐模板生效的——可以让"补偿协议"模板走本地、其他模板继续走 qwen-long，便于灰度。

## PaddleOCR 部署（仅全离线方案需要）

采用 PP-OCRv5 + PaddleX serve（CPU 模式，不抢 4090 显存）：

```bash
# 1. 起一个空容器
docker run -d --name paddlex-serve -p 8080:8080 \
  --restart unless-stopped \
  ccr-2vdh3abv-pub.cnc.bj.baidubce.com/paddlex/paddlex:paddlex3.0.0-paddlepaddle3.0.0-cpu \
  tail -f /dev/null

# 2. 容器内安装 OCR 依赖并启动 serve（首次会下载模型，约 5 分钟）
docker exec -d paddlex-serve bash -c \
  "pip install -U paddleocr && \
   paddlex --serve --pipeline OCR --host 0.0.0.0 --port 8080"

# 3. 验证（有返回 ocrResults 即成功）
curl -X POST http://localhost:8080/ocr \
  -H 'Content-Type: application/json' \
  -d "{\"file\":\"$(base64 -w0 test.png)\",\"fileType\":1}" | jq '.result.ocrResults[0].prunedResult.rec_texts'
```

请求/响应契约：
- 请求：`POST /ocr`，body `{file: <base64>, fileType: 1}`（1=图片，0=PDF）
- 响应：`{result: {ocrResults: [{prunedResult: {rec_texts: [...], rec_scores: [...]}}]}}`

## 实施方案（不影响线上 qwen-long）

### 数据库零改动

`review_prompt_template.model_name` 已经是字符串字段。约定：
- 留空 / `qwen-long` → 走原 DashScope `chatLong`
- `ollama:qwen3.6:35b-a3b-q4_K_M` → 走本地 ollama

### 代码改三处

#### 1. `application-{profile}.yml` 加 ollama 配置

```yaml
spring:
  ai:
    ollama:
      base-url: http://<4090服务器内网IP>:11434
      chat:
        options:
          num-ctx: 16384
          temperature: 0.2
          top-p: 0.8
review:
  ai:
    local:
      enabled: true
      model: qwen3.6:35b-a3b-q4_K_M
```

#### 2. `AiChatService` 加 `chatLongLocal`

注入第二个 `ChatClient`（基于 spring-ai-alibaba 自带的 `OllamaChatModel`），写死 `think:false` + `format:"json"`。原 `chatLong` 不动。

#### 3. `ReviewAgent.callAi` 加路由

读 `template.modelName`，前缀 `ollama:` 的走 `chatLongLocal`，否则走原 `chatLong`。其他文件类型分支（图片、空表单）保持不变。

### 前端零改动后台 + 一处下拉补充

ai 模型下拉里增加一个选项：`ollama:qwen3.6:35b-a3b-q4_K_M (本地·补偿审核)`。

## 风险与缓解

| 风险 | 概率 | 缓解 |
|---|---|---|
| 4090 显存爆 | 低 | 已实测 23GB / 24GB，留 1.5GB headroom；num_ctx 不超 16K |
| 本地模型 JSON 输出不稳 | 低 | 已开 `format:"json"` + `/no_think`，5 规则测试 100% 命中 |
| 4090 服务器宕机 | 中 | 监控 ollama 健康；失败直接报错让用户重审 |
| 18 页超长文档超过 16K token | 低 | 实际打印件平均 6~10K，扫描件 OCR 噪声大些；超长时按规则分批审核（后续优化）|
| qwen3.6 在边缘 case 上不如 qwen-long | 中 | 模板字段 `model_name` 可逐项目灰度，先在补偿协议这一类启用 |
